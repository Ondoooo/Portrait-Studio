# Evaluating candidates and changes

## 1. Candidate selection

Draw a 256 × 160 packing label with a soft gray fold and a tiny black lot number. Create a reference, a version with a local defect, and three repairs. In one repair displace the fold slightly. In another restore the fold and damage a single lot-number stroke. In a third leave a conspicuous double edge. Include a second batch in which every repair damages the number. The requested result restores the fold and preserves the number.

Show shuffled whole-label views and registered native crops. Record a verdict before showing reference-error scores or revealing the methods. Compare the smallest whole-frame error rule with a rule that independently records task completion, protected print and suitability for delivery. Try exchanging the order of the letters and include an identical pair. Report any visual disagreement explicitly. A useful rule can reject every member of the second batch, recognize identical candidates, and explain why one lower-error image still fails the request. A scripted oracle cannot stand in for an independent blind visual vote. If a second reader is unavailable, leave agreement unmeasured.

## 2. Finish and stage order

Draw a wide, shaded cardboard panel with a dark border and a smooth colored swatch away from the border. Define a fixed central crop and a fixed patch with known clean pixels. Compare a clean join with a planted offset just inside the patch boundary. Cross each with a cosmetic tint on/off. Add a third input that already contains the same tint before processing. Keep patch, crop, resampling, and chosen fixture seed fixed. Save reference, pre-finish, finished and delivered stages.

Compare grading from full-image statistics before cropping with grading from crop statistics after cropping. Measure signed color differences on matched pixels near the join and on the distant swatch. Trace the first divergence in each case. Turning a setting off cannot erase an inherited effect. Require the reviewer to demonstrate this with a pair and state which historic comparisons would stay inconclusive if the input's finish history were missing. Return a small matrix and one proposed default only if its scope is supported.

## 3. Model comparisons

Use an object editing request such as “make the left shipping label green and preserve the right label.” Build two deterministic mock adapters with different documented input contracts. One takes an image and mask. The other takes an image and a text identifier for the part. Include a known-success request supported by each, a no-op path, and a planted wiring fault that drops one supported input. Record requested settings and the effective inputs actually received, using hashes for arrays.

Compare the plain instruction with one contract-specific rendering of the same intent. Evaluate selection, preservation and change separately. An adapter that received no edit request or never executed cannot earn a model quality score. A route that ran correctly but changed the wrong label should retain its failure. Return the smallest observation that distinguishes the two failures. For a proposed real adapter, cite its versioned input documentation and mark claims that still require execution. Freeze each recipe before testing another randomly placed label.

## 4. Transfer and cost

Use two mock candidate selectors or the first packet's returned object repair. Split by independent source design, keeping all crops and seeded variants of each source in the same split. Use at least one previously successful control and one different source such as a printed sign in place of a canvas pouch. Pair variants by source and seed; distinguish the first draw from the delivered selection and any fallback. Count outputs that never ran separately.

Return counts for attempted, completed, delivered, and acceptable images plus time per acceptable result, or undefined if there are none. Report per-source wins, ties, regressions and both-fail outcomes. Demonstrate how a pooled average can improve while one source consistently regresses. Record a threshold for moving a candidate into a side-by-side experimental workflow before looking at the held-out source. With only a few independent sources, report the individual results and the remaining uncertainty.
